# Y2038 与量程

## 2038 年问题是什么

2038 年问题是 32 位有符号秒计数溢出。经典 Unix 时间戳是 `time_t`：自 `1970-01-01T00:00:00Z` 起的有符号 32 位秒计数。纪元后 `i32::MAX` 秒正好是

```text
2038-01-19 03:14:07 UTC
```

再往后一秒，计数器无法表示该值，回绕成负数。任何用 32 位有符号秒存储或计算时间的代码都会撞上它。

## 为什么 tzcraft 在构造上不可能遇到

tzcraft 中每个时域都使用了把边界推得极远的宽度：

| 值 | 存储 | 量程 |
| --- | --- | --- |
| `Ticks`（唯一的瞬时类型） | 纪元起 `i128` 纳秒 | 约 ±5.4×10^21 年（存储；`i64` 秒访问器界定可用范围） |
| `timestamp*` 访问器 / `from_timestamp*` 构造器 | `i64` 秒 | 约 ±2920 亿年 |
| `Date` | 纪元起 `i32` **天** | 约 ±580 万年（从来不是秒） |
| `Offset` | `i32` 秒 | 构造时校验在 ±24 小时内 |
| `Duration::from_seconds` 等 | `i64` 秒 → `i128` 纳秒 | 约 ±2920 亿年 |

时域中唯一的 `i32` 是 `Offset`（限定 ±24 小时并校验）和 `Date` 的天数（天不是秒——±580 万年）。不存在任何把秒存在 32 位里的代码路径。

## 锁定的回归测试

`tests/y2038.rs` 锁定了边界行为，防止未来重构悄悄把 32 位秒带回来：

- `y2038_boundary_seconds` —— 精确回绕点：`2_147_483_647` 秒（`2038-01-19T03:14:07Z`）以及一纳秒后的 `2_147_483_648` 秒，含公历投影与 RFC 3339 文本往返。
- `pre_epoch_extremes_floor` —— `i32::MIN` 秒（`1901-12-13T20:45:52Z`）以及纪元前小数瞬时的 floor 语义。
- `far_future_instants_are_representable` —— 9999 年、扩展年份 10000 与 123456，以及 `i64::MAX` 整秒。
- `post_2038_text_round_trips` —— 跨越边界的 RFC 3339 往返。
- `duration_seconds_are_i64` —— 横跨整个 `i64` 秒量程的时长，以及单步大于 2³¹ 秒的位移。

运行：

```sh
cargo test --test y2038
```

## 与生态对照

- `chrono` 是 2038 安全的：瞬时用 `i64` 秒。公历量程 ±262,000 年。
- `time` 是 2038 安全的：`i64` 纳秒 + 偏移。默认公历量程为公元 0000–9999 年（`large-dates` 可扩展）。
- `rustix::time::Timespec` 用 `i64` 秒 + `i64` 纳秒——POSIX `timespec`，2038 安全。

tzcraft 的 `i128` 纳秒时间线是三者量程的超集；把值迁入 tzcraft 是精确的（见 `tzcraft::migration`），超出目标量程的值由目标库拒绝而不是回绕。
