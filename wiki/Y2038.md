# Y2038 and Range

## What the Year 2038 problem is

The Year 2038 problem is a 32-bit signed-seconds overflow. A classic Unix
timestamp is `time_t`, a signed 32-bit count of seconds since
`1970-01-01T00:00:00Z`. `i32::MAX` seconds after the epoch is exactly

```text
2038-01-19 03:14:07 UTC
```

One second later the counter cannot represent the value and rolls over to a
negative number. Any code that stores or computes time in 32-bit signed
seconds hits this.

## Why tzcraft cannot hit it

Every time domain in tzcraft uses a width that keeps the boundary far out of
reach:

| Value | Storage | Range |
| --- | --- | --- |
| `Ticks` (the only instant type) | `i128` nanoseconds since the epoch | ≈ ±5.4×10^21 years (storage; `i64`-second accessors bound the usable range) |
| `timestamp*` accessors / `from_timestamp*` constructors | `i64` seconds | ≈ ±292 billion years |
| `Date` | `i32` **days** since the epoch | ≈ ±5.8 million years (never seconds) |
| `Offset` | `i32` seconds | validated to ±24 h at construction |
| `Duration::from_seconds` and friends | `i64` seconds → `i128` nanoseconds | ≈ ±292 billion years |

The only `i32` in the time domain is `Offset` (bounded to ±24 hours and
validated) and the `Date` day count (a day is not a second — ±5.8 million
years). There is no code path that stores seconds in 32 bits.

## Pinned regression tests

`tests/y2038.rs` locks the boundary behaviour so a future refactor cannot
silently reintroduce a 32-bit second:

- `y2038_boundary_seconds` — the exact rollover point: `2_147_483_647` s
  (`2038-01-19T03:14:07Z`) and one nanosecond later `2_147_483_648` s,
  including the civil projection and RFC 3339 text round-trip.
- `pre_epoch_extremes_floor` — `i32::MIN` seconds (`1901-12-13T20:45:52Z`)
  and floor semantics for pre-epoch fractional instants.
- `far_future_instants_are_representable` — year 9999, expanded years
  10000 and 123456, and `i64::MAX` whole seconds.
- `post_2038_text_round_trips` — RFC 3339 round trips across the boundary.
- `duration_seconds_are_i64` — durations spanning the whole `i64` second
  range, and shifts larger than 2³¹ seconds in one step.

Run them with:

```sh
cargo test --test y2038
```

## Comparing to the ecosystem

- `chrono` is 2038-safe: its instants use `i64` seconds. Its civil range is
  ±262,000 years.
- `time` is 2038-safe: `i64` nanoseconds since midnight with an offset. Its
  default civil range is years 0000–9999 (`large-dates` extends it).
- `rustix::time::Timespec` uses `i64` seconds + `i64` nanoseconds — POSIX
  `timespec`, 2038-safe.

tzcraft's `i128`-nanosecond timeline is a superset of all three; porting a
value into tzcraft is exact (see `tzcraft::migration`), and out-of-range
values are rejected by the target library rather than wrapped.
